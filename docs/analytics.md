# Аналитика: доступы и ежедневный цикл

Три источника данных и скиллы, которые их читают.

## Источники

| Источник | Что показывает | Доступ |
|---|---|---|
| **PostHog** (EU) | поведение на сайте: визиты, каналы, воронка чата | Personal API key, scope `Query Read` |
| **Search Console** | поисковый спрос: показы, позиции, индексация | OAuth-клиент Desktop, scope `webmasters.readonly` |
| **Rush Analytics** | съём выдачи со стороны: позиции, частотность, топ-10, подсказки, индексация, упоминания в ответах ИИ | API-ключ в `RUSH_API_KEY`, тариф Pro и выше |

Важно понимать разницу: PostHog видит только тех, кто **уже дошёл** до сайта.
Search Console показывает тех, кто увидел нас в выдаче и **не пришёл** — а
это как раз то, что можно исправить.

## Конфигурация

Секреты живут вне репозитория, права 600:

```
~/.config/segurotenerife/analytics.env    POSTHOG_*, GSC_SITE_URL, RUSH_API_*
~/.config/segurotenerife/gsc-token.json   refresh-токен Search Console
~/.config/segurotenerife/indexation.json  кэш статусов индексации
```

### PostHog

Ключ создаётся в Account settings → Personal API keys. Достаточно scope
**Query Read**, ключ стоит ограничить одним проектом. Из-за такой привязки
`/api/projects/` отдаёт 403 — работает адрес `@current`:

```
POST https://eu.posthog.com/api/projects/@current/query/
```

### Search Console

Организационная политика GCP `iam.disableServiceAccountKeyCreation` запрещает
скачивать ключи сервис-аккаунтов, поэтому используется **OAuth-клиент типа
Desktop app** от имени владельца ресурса. Побочный плюс: не нужно отдельно
выдавать права роботу в Search Console.

```bash
pip3 install --user google-auth google-auth-oauthlib
python3 scripts/analytics/gsc_auth.py ~/Downloads/client_secret_*.json
```

> **Ловушка со сроком.** Пока OAuth-приложение в статусе **Testing**,
> refresh-токен живёт **7 дней** — отчёты замолкают без единой ошибки. Чтобы
> снять ограничение: задеплоить сайт (нужны рабочие `/privacy/` и `/terms/`),
> опубликовать приложение (**Google Auth Platform → Audience → Publish app**) и
> перезапустить `gsc_auth.py`. Если доступен тип **Internal** — публикация не
> нужна вовсе.

### Rush Analytics

Внешний съём выдачи — то, чего Search Console не показывает по своей природе.
Разделение источников важно, и размывать его нельзя:

| Вопрос | Источник | Почему не другой |
|---|---|---|
| Где нас **видели живые люди** и не кликнули | Search Console | Единственный честный журнал показов; персонализация в нём усреднена по тысячам людей |
| Где мы стоим **в обезличенной выдаче** региона | Rush Analytics | GSC не отдаёт позицию по фразе, по которой нас ни разу не показали, — ноль показов там неотличим от «нас там нет» |
| Спрос по фразе, которой у нас ещё нет | Rush (Wordstat / Keyword Planner) | В GSC её нет вовсе: он показывает только то, где мы уже засветились |

Это **дополнение** к [`seo/measuring-positions.md`](seo/measuring-positions.md),
а не отмена его правила. Правило «позицию не проверяют глазами» остаётся в силе:
запрещён ручной просмотр выдачи со своего браузера, потому что он и врёт, и
засчитывается нам же показом. Rush ходит в поиск со своей инфраструктуры — наш
показ не тратится, ряд сравним во времени.

**Контракт API** (проверен 2026-09-23 живым ключом):

```
база       https://app.rush-analytics.ru/apiv2/
авторизация  query-параметр ?apikey=<RUSH_API_KEY>   (не заголовок)
лимит      не чаще 1 запроса в секунду — иначе временная блокировка IP
схема      асинхронная: создать задание → опросить /status/ → забрать /result/
```

| Метод | Ручка | Зачем |
|---|---|---|
| GET | `/balance/` | остаток лимитов тарифа |
| GET | `/projectids/?typeid=3` | перечень заведённых проектов |
| POST | `/ranktracker/` | задание на съём позиций |
| GET | `/status/` | готовность задания |
| GET | `/result/ranktracker/positions_history/{projectid}/` | история позиций |
| POST | `/indexation/` | проверка индексации по адресам |
| POST | `/wordstat/`, `/adwords/` | частотность |
| POST | `/suggestions/`, `/top10/` | подсказки и разметка выдачи |
| POST | `/ai-results-tracker/` | упоминания бренда в ответах языковых моделей |

**Что нужно знать до первого прогона:**

- **Аккаунт общий с другими проектами.** На ключе висят 28 проектов чужих
  доменов (`zolotenkov.ru`, `otdano.ru`, `zorizavod.ru`), баланс — один на всех.
  Наших проектов на 2026-09-23 нет ни одного: ряд позиций начинается с нуля.
- **Один проект на одну поисковую систему.** Сервис не помечает движок в
  выдаче, и смешанный проект даёт таблицу, которую потом нельзя приписать ни
  Google, ни Яндексу.
- **Свежесозданный проект отдаёт болванку**, неотличимую от «мы нигде не видны»:
  полный комплект строк, позиция ровно на отсечке глубины, пустые посадочные
  адреса. Такой снимок отклоняется, а не «чинится» нулями. Первый настоящий
  сбор — примерно через четверть часа после создания.
- **Цена индексации считается за адрес и за систему.** Полный обход карты сайта
  на 164 страницы × 4 локали — заметная сумма из общего баланса. Перед большим
  обходом — пробный прогон на нескольких адресах.
- **Ключ не печатается.** Ни в комментарии, ни в логе, ни в выводе скрипта —
  только имя переменной. Ответ ручки `/status/` содержит ключ прямо внутри
  ссылки на результат: из такого ответа берётся только поле статуса.

## Инструменты

```bash
python3 scripts/analytics/healthcheck.py                  # живы ли доступы
python3 scripts/analytics/snapshot.py --days 30           # история метрик по дням
python3 scripts/analytics/report.py --days 28 --compare   # трафик + динамика
python3 scripts/analytics/indexation.py --limit 200       # что в индексе
python3 scripts/analytics/suggest.py --json /tmp/s.json   # подсказки Google (месячный слой)
python3 scripts/validate_articles.py                      # контент перед сборкой
```

Ни один из них не требует сторонних библиотек — только стандартная библиотека,
чтобы регулярный запуск ничего не ломал. `google-auth` нужен лишь для разовой
авторизации.

`healthcheck.py` возвращает ненулевой код, если доступ потерян или контент
написан, но не задеплоен. Он идёт первым шагом рутины именно поэтому: без
токена остальные инструменты не падают, а печатают нули, и отчёт выглядит как
«трафика нет».

`snapshot.py` копит `docs/seo/metrics.csv` — по строке на день. Search Console
не отдаёт исторический срез «какая была позиция на такую-то дату», только
агрегат за период, поэтому историю приходится вести самим.

Данные Search Console финализируются с задержкой около двух суток, поэтому
отчёт всегда берёт окно, заканчивающееся позавчера.

Собственные визиты в PostHog не попадают: админка (`admin.segurotenerife.com`)
аналитику не подключает вовсе — трекинг там отключён на уровне кода
(`shared/api/src/posthog.ts`, `isInternalSurface()`). Раньше исключалось только
событие `admin_opened`, а просмотры страниц админки шли в отчёт как обычный
трафик. Фильтры в `report.py` остались для истории: `INTERNAL_EVENTS`
(`admin_opened`) и `INTERNAL_HOSTS` (`admin.*` по `properties.$host`) — данные до
сентября 2026 без них по-прежнему завышены.

Квоты URL Inspection: 2000 запросов в сутки. Проиндексированные URL
перепроверяются раз в неделю, проблемные — каждый запуск.

## Ежедневный цикл

1. `healthcheck.py` — доступы и инварианты. Отказ останавливает рутину.
2. `snapshot.py` — дневной срез в историю.
3. `/seo-analyst` — читает данные, сверяет с порогами, ставит задачи.
4. `/seo-daily-article` — берёт тему из очереди и публикует статью дня.
5. `/seo-copywriter` — выполняет задачи аналитика, валидирует, пишет в CHANGELOG.
6. История решений накапливается в `docs/seo/journal.md`, числовая — в
   `docs/seo/metrics.csv`.

Недельный (`/seo-weekly`) и месячный (`/seo-monthly`) слои, форматы отчётов,
расписание и правила эскалации — в [`seo/pipeline.md`](seo/pipeline.md).

Правила принятия решений — в самих скиллах (`.claude/skills/`). Там же записано
главное: «изменений нет, действий не требуется» — нормальный результат дня.
